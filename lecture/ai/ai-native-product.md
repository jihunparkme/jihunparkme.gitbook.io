# '정책 알림이' 핵심 타겟 페르소나 2종

## 페르소나 1. 김서연 — "정보 과부하형 초산 맘"

### 인구통계
- **나이/성별**: 만 33세, 여성
- **상황**: 임신 20주차 (첫 아이)
- **직업**: 중견 IT기업 마케터 (맞벌이, 서울 마포구 거주)
- **가구 월소득**: 약 800만 원 (부부 합산)

### 핵심 특징 및 성격
- 꼼꼼하고 계획적. 임신 사실을 알자마자 맘카페·블로그·앱을 모두 가입함
- 디지털 네이티브로 모바일로 모든 것을 해결하며, 편리한 서비스에 기꺼이 시간을 투자함
- "손해 보기 싫다"는 성향이 강하고, 첫 육아라 놓치는 것에 대한 불안이 큼

### Pain Point
- 정보가 정부(복지로, 정부24), 시·구청, 카드사, 회사 복지 등으로 흩어져 있고 용어가 어려움 (예: 첫만남이용권, 부모급여, 임신·출산 진료비 바우처)
- 소득 기준·거주지 조건이 복잡해 **내가 대상자인지 판단하기 어려움**
- 신청 시기를 놓쳐 혜택을 못 받는 사례를 커뮤니티에서 보고 불안해함
- 출산휴가·육아휴직 급여 등 회사 제도와 국가 제도의 중복·연계 파악이 어려움

### 우리 서비스의 가치
- 임신 주차·거주지·소득 입력 한 번으로 **내게 맞는 정책만 선별 추천**
- 신청 기간 D-day 알림으로 **"놓칠 걱정" 제거**
- 복잡한 정책을 쉬운 말로 요약하고 신청 경로를 바로 연결 → 탐색 시간 절감, 수령 가능 금액을 한눈에 확인

## 페르소나 2. 박민수 — "바쁜 다자녀 맞벌이 아빠"

### 인구통계
- **나이/성별**: 만 38세, 남성
- **상황**: 자녀 2명 (5세, 8개월), 둘째 출산 후 육아휴직 고민 중
- **직업**: 제조업 중소기업 대리 (경기도 화성시 거주, 아내는 간호사 교대근무)
- **가구 월소득**: 약 600만 원

### 핵심 특징 및 성격
- 가정적이고 책임감이 강하나 업무·육아로 시간이 극히 부족함
- 실용주의자. 정보를 직접 찾기보다 "핵심만 알려주면 바로 신청"하는 스타일
- 정책 정보는 주로 아내나 지인에게 듣고, 공식 사이트 이용엔 익숙하지 않음

### Pain Point
- 첫째 때와 **제도가 바뀌어** 달라진 내용을 따라가기 어려움 (부모급여 확대, 육아휴직 급여 상향, 6+6 부모육아휴직제 등)
- 다자녀 혜택(주거·교통·교육·세제)이 중앙·지자체별로 달라 한눈에 보기 어려움
- 평일 근무 중 구청 방문이 불가능해 **온라인 신청 가능 여부**가 중요함
- 아빠 육아휴직 관련 정보와 회사 눈치로 인한 정보 접근성 부족

### 우리 서비스의 가치
- 자녀 연령·수, 거주 지자체 기반으로 **다자녀·아빠 육아 특화 정책 추천**
- "온라인 신청 가능", "소요 시간 5분" 등 **실행 난이도 정보** 제공
- 자녀 성장 단계별(영아→유아→초등) 자동 알림으로 **정책 변화와 신규 혜택을 능동적으로 안내**
- 배우자와 알림 공유 기능으로 가족 단위 정책 관리

## 핵심 운영 제안

### 1. North Star Metric
`월간 신청(이동) 완료 정책 수 ÷ 활성 유저`

### 2. 퍼널 관리
가입 → 프로필 완료 → 첫 추천 → 알림 반응 → 신청 이동 순으로 단계별 이탈을 추적합니다.

### 3. 페르소나별 세분화

| 페르소나                 | 중점 지표                    |
| ------------------------ | ---------------------------- |
| **김서연** (임신·초산)   | 알림 반응률, D-day 알림 효과 |
| **박민수** (다자녀 아빠) | TTV, 온라인 신청 전환율      |

### 4. MVP 성공 판단 기준 (예시)
출시 후 8~12주 시점에 프로필 완료율, 알림 반응률, 4주 리텐션, 신청 전환율 중 **3개 이상** 달성 시 성공

### 5. 측정 한계 대응
신청 완료는 외부 사이트에서 이뤄지므로 **"신청 페이지 이동 + 사후 알림('신청하셨나요?')"**으로 대리 측정합니다.

## 1. 정책 데이터 수집·정제의 어려움

**문제**
- 정책이 복지로, 정부24, 지자체 사이트, 공공데이터포털 등에 흩어져 있고 형식이 제각각입니다.
- 소득·거주지·연령 조건이 자연어로 서술되어 구조화가 어렵고, 지자체 정책은 API가 없는 경우가 많습니다.

**대응**
- MVP는 **공공데이터포털 API(복지서비스 목록·상세)** 중심으로 시작하고, 지자체는 **서울·경기 등 2~3곳으로 제한**합니다.
- 정책 조건은 `지역/연령/소득구간/자녀수/임신여부`의 **표준 스키마**로 정의하고, LLM 1차 추출 후 **운영자 검수(Human-in-the-loop)**를 거칩니다.
- 핵심 정책 상위 30~50개는 수기로 큐레이션합니다.

## 2. AI 추천 오류(환각)와 신뢰 문제

**문제**
- 소득 기준·금액·기한을 잘못 안내하면 사용자가 손해를 보고 신뢰를 잃습니다.
- LLM이 존재하지 않는 정책을 만들어낼 위험이 있습니다.

**대응**
- **자격 판정은 규칙 기반(룰 엔진)**, LLM은 **설명 요약·문장 생성**에만 사용합니다.
- 모든 추천에 **원문 링크와 최종 확인일**을 표시하고, 검증된 DB 데이터에 한정한 **RAG 구조**를 적용합니다.
- "대상일 수 있음(참고용)" 문구와 👍/👎 피드백 버튼을 두고, 오답 신고를 운영 지표로 관리합니다.

## 3. 개인정보·민감정보 처리

**문제**
- 소득, 임신 여부, 자녀 정보는 민감하며 개인정보보호법 대상입니다.
- 외부 LLM API 전송 시 유출 우려가 있습니다.

**대응**
- **최소 수집**: 정확한 소득 대신 구간, 생년월일 대신 연령대·개월 수를 받습니다.
- LLM 호출 시 **식별 정보를 제거**하고 조건값만 전달하며, 전송·저장 모두 암호화합니다.
- 동의 항목을 분리(필수/선택/알림 수신)하고, 탈퇴 시 즉시 삭제하며, 출시 전 **법무 검토**를 받습니다.

## 4. 정책 변경·종료에 따른 데이터 노후화

**문제**
- 정책은 연초·예산 변경·지자체 공고에 따라 수시로 바뀌며, 오래된 정보는 핵심 가치("놓치지 않게")를 훼손합니다.

**대응**
- **일 단위 수집 배치 + 변경 감지(diff)**로 변경 시 운영자에게 알립니다.
- 정책별 `last_verified_at`을 두고 30일 이상 미검증 시 경고 배지를 표시합니다.
- 월 1회 핵심 정책 전수 점검을 운영 체크리스트에 포함합니다.

## 5. 알림 발송 인프라·피로도

**문제**
- 신청 기간 직전 알림이 몰려 큐 지연이 생길 수 있고, 과다 발송은 해지로 이어집니다.
- 카카오 알림톡은 템플릿 심사와 비용이 필요합니다.

**대응**
- 메시지 큐(SQS 등) 기반 비동기 발송과 **재시도·중복 방지(idempotency key)**를 적용합니다.
- 사용자당 **주 2~3회 상한**, D-7/D-1 규칙 기반 스케줄, 유형별 수신 설정을 제공합니다.
- MVP는 **푸시 + 카카오 알림톡 1채널**로 시작하고 템플릿 심사를 일찍 진행합니다.

## 6. 외부 API·LLM 비용과 의존성

**문제**
- 공공 API는 장애·호출 제한이 있고, LLM 비용은 사용자 증가에 따라 빠르게 늘어납니다.

**대응**
- 수집 데이터를 **자체 DB에 캐싱**하고 런타임에서 외부 API를 직접 호출하지 않습니다.
- 정책 요약은 **사전 생성 후 저장**하고, 소형 모델부터 적용합니다.
- LLM 공급자 **추상화 레이어**를 두고, 일일 호출 상한과 비용 모니터링을 설정합니다.
